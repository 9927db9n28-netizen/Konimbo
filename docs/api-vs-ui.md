# API או ממשק ניהול? — מדריך החלטה

**כלל אצבע:** API לפעולות על **נתונים** (מוצרים, מחירים, מלאי, הזמנות, לקוחות) — בכמות, בדיוק ובחזרתיות.
ממשק לפעולות **הגדרה ועיצוב** שאין להן endpoint, או לפעולה חד-פעמית על פריט אחד.

| משימה | דרך מומלצת | למה |
|---|---|---|
| עדכון מחירים / מבצע על הרבה מוצרים | **API** (`PUT /items`) | מהיר, ניתן לגיבוי ולשחזור; `origin_price` מציג מחיר לפני מבצע |
| עדכון מלאי | **API** (`quantity` / `inventory`) | מלאי מורכב: יש להקים את סוג השדרוג קודם בממשק |
| SEO (title/description/slug) לקטלוג | **API** | שדות `seo_*` |
| הוספת מוצר חדש בודד עם תמונות ותיאור עשיר | ממשק או API | בממשק רואים תצוגה מקדימה; API אם יש הרבה |
| ייבוא/ייצוא קטלוג גדול | **API** (או ייבוא אקסל בממשק) | מגבלת 100 קריאות/10 דק' — לתכנן אצוות |
| סינונים, תגים, קטגוריות משניות למוצר | **API** | נוצרים אוטומטית אם חסרים |
| דוח הזמנות / מכירות | **API** (`GET /orders` + סינון תאריכים) | ניתוח מותאם |
| עדכון סטטוס הזמנה | **API** (הוספת status) | חייב להיות קיים ב"מצבי הזמנה" כדי לשנות מצב |
| שיוך לקוח למועדון | **API** (`discount_title`) | |
| יצירת קטגוריה עם עיצוב / עריכת תפריט | **ממשק** | אין endpoint לכתיבת קטגוריות (רק קריאה) |
| עיצוב, דף הבית, באנרים, תבניות | **ממשק** | אין API |
| קופונים ומבצעים, מועדוני לקוחות (הגדרה) | **ממשק** | הגדרת הקופון/מבצע היא בממשק; ב-API רק הנחה לעגלה |
| אפשרויות משלוח ותשלום, הגדרות חנות | **ממשק** | |
| אינטגרציה קבועה עם מערכת חיצונית | **מערכת האינטגרציות** + Webhook | רץ בשרתי קונימבו, בלי שרת משלך |
| מחיקת מוצרים | API או ממשק — **רק באישור** | ה-DELETE מעביר לפח (ניתן לשחזור) |

## סדר עבודה לכל שינוי דרך API
1. GET למצב הקיים → גיבוי ל-`backups/`.
2. Dry-run — להציג מה ישתנה.
3. אישור מנהל האתר.
4. ביצוע בקצב שמכבד את מגבלת הקריאות.
5. אימות (GET חוזר) ודיווח.
